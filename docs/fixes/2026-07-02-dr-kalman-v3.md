## Какво се промени

### 1. Нов клас: `DeadReckoningKalman.kt` (467 реда)

6-state Kalman филтър с gravity removal, Earth-frame преобразуване,
и физически коректен модел без изкуствен speed decay.

**State vector:** `[posN, posE, velN, velE, biasN, biasE]`

#### Ключови дизайнерски решения:

1. **Само bias states са novelty** — не са нужни attitude/gyro bias states.
   GPS velocity + position са достатъчни за да се наблюдават position, velocity,
   и accelerometer bias (чрез velocity innovation). Attitude не се нуждае от
   Kalman correction — rotation vector сензорът е достатъчно точен.

2. **Няма speed decay** (закон на Нютон). При нулево ускорение скоростта остава
   константна. Това е фундаментално различно от v1 и v2 които или имаха drag
   decay, или разчитаха на exponential smoothing.

3. **Bias states** се оценяват чрез process noise, не чрез отделен measurement.
   При GPS ON: innovation-ът в скоростта индиректно коригира bias.
   При GPS OFF: bias-ът остава на последната оценена стойност.

4. **Lazy initialization** — Kalman се инициализира при първия GPS fix (още преди
   DR да е активен). Това дава време на bias states да конвергират.

#### Матрични операции (без външна библиотека):
- `predict(dt, accelN, accelE)` — F*x + B*u + Q
- `updateWithGPS(gpsPosN, gpsPosE, gpsVelN, gpsVelE, accuracy)` — K*(z - H*x)
- `invert4x4()` — Gauss-Jordan elimination за 4×4 innovation covariance

### 2. Continuous Sensor Pipeline (`LocationService.kt`)

**Преди:** Сензорите се регистрират само при GPS загуба (`registerDrSensors()`)
с 5-секунден activation delay. Това създаваше cold-start проблем
— Kalman беше ненаучен, gravity току-що започваше да се филтрира,
rotation matrix още не беше стабилна.

**Сега:** Сензорите са регистрирани ПОСТОЯННО в `onCreate()`:
```kotlin
override fun onCreate() {
    // ... initial setup ...
    registerDrSensorsContinuously()  // <-- ТУК, винаги
}
```

`Kalman.predict()` се вика на **всяко** accelerometer събитие — и когато
GPS работи, и когато не. `Kalman.updateWithGPS()` се вика на всеки GPS fix.

**Резултат:**
- Няма 5s activation delay → DR стартира МОМЕНТАЛНО при GPS загуба
- Bias вече е предварително оценен от GPS-периода
- Gravity филтърът е конвергирал
- Rotation matrix постоянно се обновява

### 3. Kalman GPS Update в `onLocationChanged()`

Добавена lazy init + update логика след ring buffer:
```kotlin
if (!drKalman.isActive()) {
    drKalman.initialize(lat, lon, alt, speed, bearing, accuracy)
} else {
    drKalman.updateWithGPS(relPosN, relPosE, velN, velE, accuracy)
}
```

GPS velocity векторът се изчислява от speed × [cos(bearing), sin(bearing)] —
геометрична проекция на скаларните GPS данни в ENU frame.

### 4. Heading Sanity Filter

Нов `filterHeading()` в `LocationService.kt`:
- Плъзгащ прозорец от 5 heading стойности
- Отхвърля единични скокове > 30° от медианата
- Приема ако 3+ последователни показания са в новата посока (реален завой)
- Предотвратява wild zigzag от phone reorientation и сензорни гличове

### 5. 6-Component Snapshot при GPS загуба

При `startDeadReckoning()` се логва пълен snapshot:
```
SENSOR_SNAPSHOT: accel=[x,y,z], gyro=[x,y,z], mag=[x,y,z],
                 rot=[x,y,z], earthAccel=[N,E]
KALMAN_SNAPSHOT: velN, velE, biasN, biasE, covPos, covVel
```

### 6. Toast Feedback за UX

```kotlin
"ACTIVE (K)! speed=1.8m/s"    // DR стартиран с Kalman
"STOPPED (45s)"               // DR спрян, показва продължителност
"FAILED: ring buffer empty"    // Не може да стартира
```

"(K)" в toast-a потвърждава че ползваме Kalman режим (не trajectory).

## Рискове

1. **Battery drain** — continuous 50Hz сензори консумират 1-2% extra battery/час.
   Приемливо за навигационно приложение.

2. **Heading filter може да пропусне бърз завой** — ако завоят е < 3 reading-a
   (0.2s при 50Hz → нереалистично бързо), ще бъде отхвърлен.

3. **Bias може да дрифтва при продължителен DR** — без GPS correction, bias states
   са "замразени" на последната оценка. Process noise позволява бавна промяна,
   но без measurement, bias-ът не може да се коригира.

4. **Device orientation → vehicle heading mismatch** — ако телефонът се накланя
   по време на DR, heading-ът ще се промени дори ако посоката на движение е същата.
   Heading филтърът помага, но не решава фундаментално проблема.
